# Релизная подпись Android

Пока приложение не подписано своим ключом, оно не приложение, а сборка на твоей
машине: до этой задачи `flutter build apk --release` подписывал релиз
**отладочным** ключом из `~/.android/debug.keystore`. Такой APK не примет
магазин, а бета не обновится — Android ставит обновление поверх только если
подпись совпадает с подписью уже установленной версии.

Отладочный ключ у каждой машины свой и живёт год. Релизный — один на всё время
жизни приложения.

> **Потеряешь ключ — потеряешь возможность обновлять приложение.** Не «будет
> неудобно»: Google Play не даёт заменить подпись у опубликованного пакета,
> `applicationId` занят навсегда, и единственный выход — новое приложение в
> магазине, с нуля, без установок и отзывов. **Сделай резервную копию
> хранилища и паролей вне репозитория** — в менеджере паролей и на носителе,
> который не лежит рядом с ноутбуком.

---

## 1. Создать хранилище ключа

Одной командой, из любого каталога **вне репозитория**:

```sh
keytool -genkeypair -v \
  -keystore ~/keys/arcadelingo-upload.jks \
  -storetype JKS \
  -keyalg RSA -keysize 2048 -validity 10000 \
  -alias upload
```

Что значит каждый параметр:

| Параметр | Зачем |
|---|---|
| `-genkeypair` | создать пару ключей (закрытый + сертификат), а не импортировать чужую |
| `-v` | печатать, что получилось: увидишь alias, алгоритм и срок |
| `-keystore <путь>` | файл хранилища. **Вне репозитория** — см. шаг 2 |
| `-storetype JKS` | формат хранилища. Задан явно: keytool из JDK 9+ по умолчанию делает PKCS12 и печатает предупреждение про «устаревший JKS», сбивая с толку. Gradle работает с обоими, но вся документация Flutter и Android говорит про JKS |
| `-keyalg RSA` | алгоритм ключа. Play принимает RSA (или EC) |
| `-keysize 2048` | длина ключа. Меньше Play не примет, больше не нужно |
| `-validity 10000` | срок действия сертификата **в днях**, около 27 лет. Play требует, чтобы сертификат был действителен минимум до 22 октября 2033 года, и 10000 дней покрывают это с запасом. Ключ с истёкшим сертификатом обновлять приложение больше не сможет |
| `-alias upload` | имя ключа внутри хранилища: их там может быть несколько, и Gradle просит по имени. Пойдёт в `keyAlias` |

Команда спросит:

- **пароль хранилища** (`storePassword`) — на файл целиком;
- **пароль ключа** (`keyPassword`) — на конкретный alias. Можно сделать таким
  же, как первый: keytool предложит это по Enter;
- **имя, организацию, город, страну** — это поля сертификата. Их видно в
  `keytool -printcert` и больше нигде; приватному разработчику хватит имени и
  двухбуквенного кода страны (`KZ`). Пустыми оставлять не стоит: сертификат с
  пустым CN часть инструментов показывает как «Unknown».

## 2. Куда положить

- **Хранилище (`.jks`)** — вне рабочего дерева репозитория, например
  `~/keys/arcadelingo-upload.jks`. Не в `android/`, не в `assets/`, вообще не
  внутри каталога проекта: любой `git add -A`, любой архив каталога, любая
  синхронизация папки — и ключ уехал.
- **`android/key.properties`** — внутри репозитория, но `.gitignore` его
  прячет. Это единственный файл проекта, который сборка ждёт, а git не видит.

Оба правила проверяются тестом `test/android/release_signing_test.dart`: он
спрашивает у самого git, игнорируется ли такой путь, и требует, чтобы ничего
похожего не было в индексе. Правило можно случайно ослабить — тест покраснеет.

## 3. Что записать в `android/key.properties`

Файл создаётся руками, четыре строки:

```properties
storeFile=C:/Users/Пользователь/keys/arcadelingo-upload.jks
storePassword=<пароль хранилища>
keyAlias=upload
keyPassword=<пароль ключа>
```

- `storeFile` — путь к хранилищу. Абсолютный надёжнее; относительный считается
  **от каталога `android/`**, а не от корня репозитория.
- На Windows пиши прямые слэши или удвоенные обратные: `key.properties` — это
  Java `Properties`, и одиночный `\` в нём экранирующий. Измеренный пример:
  `storeFile=C:\keys\test-upload.jks` прочитался как `C:keys<таб>est-upload.jks`
  — `\t` стал табуляцией. Сборка отвечает на это «storeFile указывает на …, а
  такого файла нет», и путь печатается в сообщении целиком именно затем, чтобы
  такое было видно глазом.
- Пароли — как есть, без кавычек: кавычки станут частью пароля.

## 4. Проверить

Без файла релиз обязан падать понятно, а не гредловской кашей:

```
$ flutter build apk --release
FAILURE: Build failed with an exception.

* What went wrong:
Релизная сборка не подписана: нет файла ...\android\key.properties
...
Создай ключ по docs/dev/release.md — там команда keytool с разбором каждого
параметра, куда положить хранилище и что записать в android/key.properties.
```

С файлом — собираться и быть подписанным твоим ключом:

```sh
flutter build apk --release
"$ANDROID_HOME/build-tools/34.0.0/apksigner" verify --print-certs \
  build/app/outputs/flutter-apk/app-release.apk
```

`apksigner` напечатает `Signer #1 certificate DN:` — это обязано быть то имя,
которое ты ввёл на шаге 1, и **не** `CN=Android Debug, O=Android, C=US`.
Второе означает, что подпись всё ещё отладочная.

Тот же отпечаток со стороны хранилища:

```sh
keytool -list -v -keystore ~/keys/arcadelingo-upload.jks -alias upload
```

`SHA-256` отсюда обязан совпасть с `SHA-256` из `apksigner verify
--print-certs`. Это и есть доказательство, что собралось тем ключом, которым
задумано, а не тем, который случайно оказался в другом хранилище.

Debug при этом не трогается: `flutter run` и `flutter build apk --debug`
работают на машине, где `key.properties` нет вовсе. Так и задумано — иначе
свежий клон не запустился бы.

## versionCode и versionName

Оба числа живут **в одном месте** — в `pubspec.yaml`:

```yaml
version: 1.0.0+1
#        ^^^^^ ^
#        │     versionCode — целое, по нему магазин понимает «новее»
#        versionName — строка, которую видит человек
```

Дальше `flutter build` передаёт их в Gradle как `flutter.versionName` и
`flutter.versionCode`, а `android/app/build.gradle.kts` только читает:

```kotlin
versionCode = flutter.versionCode
versionName = flutter.versionName
```

Второго места, где эти числа можно поправить, нет намеренно: разъехавшись, они
дадут магазину одну версию, а экрану «о приложении» другую.

`android/local.properties` тоже содержит `flutter.versionCode` — это кэш
инструмента. Он перезаписывается при каждой сборке и в репозитории не лежит;
править его бессмысленно.

### Как бампать

| Что меняешь | Как |
|---|---|
| Новая сборка для беты или магазина | `+N` → `+N+1`. **Всегда**, при каждой заливке: Play отвергает пакет с уже виденным `versionCode`, и уменьшать его нельзя никогда |
| Заметные для человека изменения | `1.0.0` → `1.1.0` |
| Починки без новых возможностей | `1.0.0` → `1.0.1` |

`versionName` магазин не сравнивает и не проверяет — она нужна человеку,
отвечающему в отзывах «а у вас какая версия». `versionCode` — единственное, по
чему Android понимает, что сборка новее.

Сейчас в `pubspec.yaml` стоит `1.0.0+1`: первая сборка ещё не залита.

## Чего здесь нет

**CI не подписывает ничего.** `.github/workflows` гоняет `./scripts/verify.sh`
— границы слоёв, анализ, тесты — и APK не собирает вовсе. Ключа на runner'е
нет, и класть его туда сейчас незачем: заливка делается руками, а секрет в CI
до автоматизации заливки — это лишняя копия ключа в чужой инфраструктуре.
Когда понадобится, механизм известен: base64 хранилища и пароли в GitHub
Secrets, распаковка в шаг сборки. Отдельная задача Фазы 5 с отдельным
решением, а не «заодно».

**Play App Signing** — тоже Фаза 5, вместе с заведением аккаунта разработчика.
Коротко: Play может хранить настоящий ключ подписи у себя, а ты подписываешь
загружаемый пакет своим **upload-ключом** — тем самым, что создан выше (отсюда
и `-alias upload`). Тогда потеря ключа перестаёт быть катастрофой: upload-ключ
Google сбрасывает по заявке. Но включается это при первой публикации и только
тогда — до неё предупреждение в шапке файла действует буквально.
