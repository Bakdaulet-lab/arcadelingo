# Wordarcade

Ежедневное изучение английских слов через аркадные мини-игры. Flutter, mobile-first, offline-first.

План: @ROADMAP.md · Текущая спека: @SPEC.md · Состояние работы: @docs/dev/tasks.md

## Команды

- Тесты точечно: `flutter test test/<путь>` — так гоняй в цикле разработки
- Полный гейт (перед коммитом): `./scripts/verify.sh` — арх-проверка + analyze + тесты
- Только границы слоёв: `./scripts/arch_check.sh` — быстро, ~1 сек
- Голдены: локально не гоняются вовсе (умолчание `WORDARCADE_GOLDENS=off`).
  Их платформа — Linux, сторожит CI. `--update-goldens` не работает ни у кого:
  компаратор бросает из `update()`. Приёмка эталона человеком — `docs/dev/goldens.md`
- Кодоген: `dart run build_runner build --delete-conflicting-outputs`
- Запуск на устройстве: `flutter run --release` (в debug анимации тормозят, судить о «фане» нельзя)

## Архитектурный закон

Это не пожелания. `./scripts/arch_check.sh` проверяет пункты 1–3 механически.

1. `lib/domain/` НЕ импортирует `package:flutter/*`, `lib/data/`, `lib/features/`.
2. Игры в `lib/features/games/` НЕ импортируют `lib/domain/srs/`. Игра общается
   с ядром только через `ReviewSession` (`lib/domain/review/review_contract.dart`).
3. `lib/domain/` детерминирован: `DateTime.now()` внутри ЗАПРЕЩЁН, текущее время
   передаётся параметром `now` (в `srs/` — значением, в сессию — функцией). Никакого
   `Random` без seed. `lib/domain/srs/` — чистые функции.
4. Направление зависимостей: presentation → usecase → repository(абстракция) ← impl → datasource

Игра, в которой появилась логика планирования повторов, — блокер на ревью, а не замечание.

## Стиль

- НИКОГДА не редактируй `*.g.dart`, `*.freezed.dart` — только через build_runner
- Ошибки из `domain/` — через `Result`/`Failure`, не `throw`: это исходы работы. Бросают
  только ошибки вызывающего кода: невалидный аргумент при построении (данные, которые
  обязан был отсеять вызывающий слой) — `ArgumentError`; нарушение протокола вызова
  (`report()` без `nextItem()`) — `StateError`
- Новые зависимости — только после явного согласования со мной. Пакет из головы не
  добавляй: сверь на pub.dev, что он существует и живой
- Версии пакетов не пиши по памяти — `flutter pub add <имя>` резолвит актуальные

## Тесты

- Порядок TDD: падающий тест → коммит теста → реализация. В фазе реализации тесты НЕ менять
- Не подгонять тесты под код, не ставить `skip`, не глушить ошибки try/catch'ем
- Где инфраструктура может дать нужный результат сама (таймеры, жизненный цикл,
  анимации, платформенные каналы) — проверяй тест мутацией: сломай реализацию и
  убедись, что тест краснеет. Зелёный тест на сломанном коде — бутафория
- Приоритет покрытия: `domain/srs` → usecases → контракт игры → голдены UI
- Fake/in-memory реализации предпочтительнее моков

## Definition of Done

Задача не выполнена, пока в ответе нет:

1. вывода `./scripts/verify.sh` (зелёного, вставленного текстом),
2. списка изменённых файлов с одной строкой причины на каждый,
3. для UI-изменений — скриншота или обновлённого голдена с объяснением, что изменилось.

«Should work» без вывода команды — не готово.

## Грабли

- Судить об игре можно только в `--release` на реальном телефоне. Эмулятор в debug врёт по фреймтаймам.
- Кодоген медленный: не запускай build_runner, если не трогал freezed/riverpod/drift-файлы.
- Голдены зелёные ровно на одной платформе — той, где сняты. Измерено: те же
  восемь кадров дают 8 из 8 расхождений на другой ОС. Эталоны сняты на Linux,
  проверяет их CI; локальный прогон кадров выключен, кандидаты приезжают
  артефактом прогона. Решение и его цена — `docs/dev/goldens.md`.
- При компакции контекста всегда сохраняй список изменённых файлов и команды тестов.
